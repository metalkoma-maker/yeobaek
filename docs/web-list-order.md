# 웹 내려받기 시각과 계정별 원고 순서

## 동작

- TXT 파일 첫 줄에 내려받는 순간의 한국시간을 초 단위까지 표시합니다. 예: `내려받은 시각: 2026-10-15 12:04:05 (한국시간)`.
- 현재 화면의 제목과 본문을 그대로 내려받습니다. 저장되지 않은 입력도 포함하며 다운로드가 서버 저장을 요구하지 않습니다.
- 목록의 원고를 마우스로 끌어 원하는 항목의 위/아래에 놓습니다. 키보드에서는 목록 항목에 초점을 둔 뒤 Alt+↑/↓로 이동합니다.
- 순서는 계정별 서버 정보로 저장됩니다. 같은 계정의 다른 브라우저/기기에서도 같은 순서로 조회됩니다. 새 원고는 맨 위에 나타납니다.
- 순서를 한 번 직접 정한 뒤에는 원고를 편집해도 위치가 바뀌지 않습니다. 수동 순서가 없으면 기존의 최근 수정순을 사용합니다.
- 두 기기의 순서 변경이 충돌하면 다른 기기의 순서를 덮어쓰지 않습니다. 최신 목록을 보여준 뒤 다시 옮기도록 안내합니다.
- 정렬 실패는 목록 전용 상태에 표시하며 현재 작성 중인 원고/임시본/자동저장 상태를 바꾸지 않습니다.

## API와 DB

`GET /api/manuscript-order`는 본인 원고 ID와 순서 버전을 반환합니다.
`PUT /api/manuscript-order`는 `{ids: [...], version: n}`을 받습니다. 로그인, 같은 Origin, CSRF 검사와 소유권 검사를 적용합니다. 모든 현재 본인 원고를 중복 없이 포함해야 하며 순서 버전 또는 원고 집합이 달라지면 409를 반환합니다.

기존 `GET /api/manuscripts`의 배열 형식은 유지하며 반환 순서에 계정별 설정을 적용합니다. 새 `manuscript_order` 테이블만 추가합니다. 기존 원고의 본문/제목/version/수정일/글자 수/수정 이력은 정렬 저장으로 바뀌지 않습니다. 기존 DB에도 앱 초기화 시 `CREATE TABLE IF NOT EXISTS`가 적용되며 기존 테이블을 삭제하거나 재작성하지 않습니다.

웹은 약 10초 간격의 기존 조회 주기에 다른 기기의 목록 순서도 확인합니다. 입력/저장/IME 조합/복구 B 확인/드래그 중에는 목록 조회 적용을 보류하며, 정렬 이전에 시작한 늦은 조회가 새 순서를 되돌리지 못하도록 별도 세대를 검사합니다. 모바일 앱은 기존 원고 목록 새로고침으로 같은 서버 순서를 읽습니다.

## 검증

Python 임시 DB 테스트는 계정 간 비공개, 로그인/CSRF/Origin, 잘못된 ID/중복/버전, 두 세션에서의 순서 공유와 충돌, 새 원고, 재초기화, 원고 내용/이력/글자 수 보존을 확인합니다.

`tests/browser_web_features.cjs`는 가짜 API로 Chromium에서 실제 TXT 다운로드, 미국 시간대에서도 한국시간 초 단위 출력, 마우스 드래그, 새 브라우저와 재로그인, 원격 정렬 반영, 실패/409, 늦은 조회 보호와 키보드 이동을 확인합니다. 기존 연속 삭제/IME/복구 B/자동저장/undo 검증도 함께 실행합니다.

PR 전용 `web-feature-checks.yml`는 테스트만 실행합니다. production 환경, 배포 키, 운영 DB나 VPN에 접근하지 않으며 기존 수동 배포 workflow를 바꾸지 않습니다.

## 운영 반영 범위

기존 GitHub Actions 수동 배포의 서버 게이트웨이는 6개 화면 파일만 허용합니다. 이 기능은 `app.py`와 순서 테이블이 필요하므로 기존 작업을 deploy로 실행하는 것만으로 서버 기능까지 설치되지는 않습니다.

실제 운영 반영 전에는 다음을 검토합니다.

1. 적용할 코드 커밋과 현재 서버의 보호 대상 파일 지문을 확인합니다.
2. 서버 코드와 SQLite의 일관된 복구본을 별도로 준비합니다. 운영 백업 스크립트를 개발/검증에서 실행하지 않습니다.
3. 리뷰한 `app.py`를 반영하고 기존 앱 서비스가 새 코드를 불러오도록 재시작합니다. 추가 테이블은 기존 데이터와 호환되며 파일 롤백 시에도 제거할 필요가 없습니다.
4. 로그인/목록/저장/이력과 새 순서 API의 상태를 검증합니다. 승인된 서버 코드 변경 뒤에는 기존 게이트웨이의 보호 기준도 그 변경과 일치하도록 별도로 검토해야 합니다. 보호 검사를 끄거나 다른 파일 변경을 일괄 승인하지 않습니다.
5. 기존 수동 웹 배포로 화면 파일을 반영합니다. 서버 API가 아직 없는 상태에서도 기존 작성/내려받기는 동작하며 드래그 순서 저장만 비활성화됩니다.

이 PR은 운영 코드/DB 변경 실행이나 배포를 수행하지 않습니다. 서버 반영 절차는 사용자의 운영 배포 승인 후 진행합니다.
