# 운영 서버·웹 배포

## 탈퇴 기록 보호 기능의 최초 반영 전

`app.py`의 탈퇴 기록 보호 버전을 처음 운영에 배포하기 **전에**, 검토한 같은 버전의 `deploy/activate_withdrawal_ledger.py`를 운영 서버에서 관리자 권한으로 한 번 실행해야 합니다. 이 도구는 기존 암호화 Drive 원격지에 시작 기록을 올려 다시 읽고, 운영 DB에 시작 표식과 삭제 보호 트리거를 추가합니다. 기존 회원·원고·백업은 변경하지 않습니다. 서비스가 가동 중이어도 짧은 DB 스키마 잠금이 발생하며, 활성화부터 새 앱 코드 배포까지 기존 앱의 회원 탈퇴는 보호 트리거 때문에 차단됩니다.

활성화의 `status`가 `activated` 또는 `already_active`이고 새 코드 배포의 건강 검사가 통과한 뒤, 가짜 회원으로 탈퇴 성공·Drive 연결 실패 시 재시도·앱 재시작 시 기록 재적용을 검증합니다. 새 코드가 시작할 때 운영 DB의 표식과 Drive 기록을 확인하지 못하면 서비스를 시작하지 않습니다. 기존 코드로 되돌려도 트리거가 남아 기록 없는 탈퇴는 차단됩니다. 실제 DB 백업 복원은 [탈퇴 기록 복원 절차](database-restore-withdrawals.md)를 따릅니다. 운영 적용 전에는 기존 약관·개인정보처리방침의 보관 설명도 새 내부 ID 기록과 일치하도록 확정해야 합니다.

## 2026-10-17 WAL 배포 도구 수정

최초 코드 배포에서 `attempt to write a readonly database`가 나왔다면 배포 도구가 이전 코드와 서비스 건강 상태를 복원했는지 Actions 로그와 `inspect`에서 먼저 확인합니다. WAL DB를 읽는 동안 배포 계정에 원고 DB 폴더의 쓰기 권한을 추가하지 않습니다. 수정된 게이트웨이는 서비스를 멈춘 뒤 DB와 남은 WAL을 배포 상태 폴더 안의 임시 복사본으로 가져와 SQLite 사본을 만듭니다. 추가 표 검증은 WAL이 없는 DB를 읽기 전용으로 열 수 있도록 조정했습니다.

리뷰한 같은 커밋의 `deploy/actions_gateway.py`와 `deploy/repair_wal_gateway.py`를 서버의 같은 폴더에 복사한 뒤 관리자 권한으로 `sudo /usr/bin/python3 deploy/repair_wal_gateway.py`를 **한 번** 실행합니다. 또는 두 파일을 담은 검증된 `.pyz` 단일 파일을 서버에 복사해 `sudo /usr/bin/python3 /경로/복구파일.pyz`를 한 번 실행합니다. 스크립트는 설치된 이전 파일과 새 파일의 SHA256을 고정값으로 확인하고, 기존 게이트웨이 사본을 남기며, 제한된 계정의 `inspect`가 성공하지 않으면 이전 파일로 돌립니다. 앱 파일, DB, 서비스는 변경하지 않습니다. 이후 GitHub Actions에서 `deploy`를 새로 실행합니다. 실패한 작업의 `Re-run jobs`는 기존 커밋/실행 문맥을 재사용하므로 새 커밋의 수정을 반영하지 않습니다.

현재 배포 대상은 `app.py`와 웹 파일 6개입니다. 기존 회원·원고·수정 이력·자동 백업 파일은 배포 ZIP에 넣지 않습니다. 이력·계정 변경은 기존 `manuscript_order` 표를 유지하고 `manuscript_checkpoints`, `schema_migrations`, `password_resets` 표를 추가합니다. 처음 도입한 버전은 최근 수정 이력을 복원 지점으로 한 번 복사했지만, 현재 버전은 새 복사본을 만들지 않고 이미 복사된 행도 화면·복원 API에서 제외합니다. 기존 원고 본문과 최근 수정 이력은 다시 쓰지 않습니다.

기존 서버 배포 도구는 `add-manuscript-order-v1`만 승인하므로 이 버전을 그대로 써서 새 표를 배포하지 않습니다. 배포 전 `deploy/upgrade_history_gateway.py`와 같은 커밋의 `deploy/actions_gateway.py`를 서버에 전달한 뒤, 관리자 권한으로 업그레이드 도구를 한 번 실행합니다. 도구는 설치된 이전 파일과 새 파일의 SHA-256을 확인하고, 서버 앱 파일·DB·서비스의 fingerprint가 바뀌지 않았는지 `inspect`로 검사합니다. 실패하면 이전 배포 도구를 복구합니다. 앱·DB·서비스는 이 단계에서 변경하지 않습니다. 이후 GitHub Actions의 `inspect`에서 `code-and-additive-history-account-v1`을 확인합니다.

## 처음 한 번: 배포 전용 계정 전환

기존 GitHub Actions/Tailscale 설정과 `/etc/yeobaek-actions.json`, `yeobaek-deploy` 계정이 먼저 있어야 합니다. 서버 관리자는 검토한 Git 커밋의 파일을 서버에 가져와 한 번만 실행합니다. 설치 도구가 실행 중인 서비스의 `DATABASE_PATH`와 작업 폴더에서 실제 운영 DB 경로를 알아내고, 파일 존재와 무결성을 검사합니다.

```sh
sudo /usr/bin/python3 deploy/upgrade_code_deploy.py
```

기존 `authorized_keys`에 배포용 Ed25519 공개키가 정확히 하나 없으면 `--public-key-file /공개키/경로`를 추가합니다. 개인키를 서버에 복사하거나 채팅에 붙이지 않습니다. 다른 SSH 키 파일·키 인증 명령·사용자 인증서가 있으면 기존 권한을 우회하지 못하도록 설치를 거절합니다. 스크립트는 운영 DB나 앱 코드를 배포하지 않습니다. 기존 설정·SSH 공개키 파일은 별도 이름으로 보관한 뒤, 공개키의 SSH 권한을 고정 명령 하나로 제한합니다. 설치 결과는 `inspect`로 조회합니다.

설치 도구는 일곱 배포 파일만 배포 계정 소유로 바꾸고, 해당 디렉터리에 쓰기 ACL을 줍니다. 운영 DB 파일에는 읽기 ACL만 부여해 SQLite 온라인 사본을 만들 수 있게 합니다. `sudoers`는 설정된 서비스의 `systemctl stop`·`start` 두 명령만 허용합니다. 배포 공개키는 Tailscale IPv4에서 온 고정 명령에만 사용할 수 있습니다. 배포 계정에 root 셸이나 일반 SSH 명령 권한을 주지 않습니다. `setfacl`, `sudo`, `visudo`, `runuser`가 없는 서버에서는 설치 전에 중단합니다. 이 일회성 작업 후에는 서버에서 배포 명령을 반복 실행할 필요가 없습니다.

## 이후 배포

코덱스에서 운영 반영을 명시적으로 요청하면, 검증·리뷰한 기능 변경을 `main`에 반영한 뒤 **`.github/deploy-request.json`만 바꾸는 별도 PR**을 만들어 병합합니다. 이 파일의 `source_commit`은 병합 직전 `main` 커밋이고 `request_id`는 매 요청마다 새로 만든 32자리 16진수입니다. 해당 파일이 바뀌는 `main` push만 배포 workflow를 시작합니다. workflow는 변경 파일이 정확히 이 파일 하나인지, 요청의 `source_commit`이 실제 직전 커밋인지, 실행 커밋이 현재 `main`인지 테스트 전과 운영 접근 직전에 확인합니다. 조건이 다르면 서버에 접근하지 않습니다. 기능 PR을 병합하는 것만으로는 운영 배포가 시작되지 않습니다. 이렇게 하면 사용자가 GitHub 화면에서 배포 버튼을 누르거나 서버 터미널을 열 필요가 없습니다. 기존 `production` Environment의 승인 정책이 별도 검토를 요구하면 그 GitHub 승인만 필요할 수 있습니다.

GitHub Actions의 **여백 웹 배포**를 `main`에서 수동 실행하는 경로도 유지합니다. `inspect`는 조회만 합니다. `deploy`와 `rollback`도 먼저 서버를 조회하고 같은 결과의 fingerprint로 작업합니다. 입력할 해시는 없습니다. `production` Environment의 기존 승인·Tailscale OAuth·SSH 호스트 키 검증을 유지합니다. 서버 도구가 새 코드 배포 기능을 보고하지 않으면 작업은 거절됩니다.

`deploy`는 가짜 데이터 테스트와 브라우저 검증을 통과한 커밋에서 허용된 일곱 파일만 묶습니다. 서버는 배포 제외 코드의 변조, 서비스 상태, 파일 해시를 먼저 검사합니다. 이후 기존 코드 파일을 백업하고 서비스를 잠시 멈춰 SQLite 온라인 사본을 만듭니다. 코드 파일을 원자적으로 교체한 뒤 서비스를 시작하고, 화면 응답 해시·새 서버 기능 표식·새 표와 이관 표식을 검사합니다. 검사에 실패하면 이전 코드 파일을 복원하고 서비스를 다시 시작합니다. 중단 기록이 남으면 다음 배포를 차단하고 `rollback`으로 복구하도록 합니다.

DB 사본은 서버의 제한된 배포 상태 폴더에만 남깁니다. 실패 또는 `rollback` 때 **코드만** 자동 복원합니다. 추가된 표는 호환되는 변경이므로 유지하며 회원·원고·수정 이력을 자동으로 이전 시점으로 되돌리지 않습니다. DB 전체 복원은 이후 사용자 입력을 지울 수 있으므로 별도 관리자 검토가 필요합니다. 기존 자동 백업 작업과 설정은 변경하거나 실행하지 않습니다.

업그레이드한 배포 도구는 `app.py`와 웹 파일 6개, 위 세 표와 이관 표식 추가만 승인합니다. 다른 Python 파일, 의존성, DB 표 삭제·변형, 서버 설정과 모바일 앱은 새 검토·배포 절차가 필요합니다. 비밀번호 찾기 메일은 배포 도구가 설정하지 않으므로 운영 서비스의 `SMTP_HOST`, `SMTP_FROM`, `APP_PUBLIC_URL`과 필요 시 SMTP 인증 정보를 별도로 준비하고 발송을 확인해야 합니다.

여백 전용 Gmail을 사용하는 최초 메일 설정은 검토한 `deploy/configure_gmail_recovery.py`를 서버에 전달한 뒤 관리자 권한으로 한 번 실행합니다. 이 도구는 기존 배포 전용 계정에 root 권한을 추가하지 않습니다. 앱 비밀번호는 실행 중 터미널에서 직접 입력하며 GitHub 배포 ZIP·저장소·채팅에 넣지 않습니다. Gmail 시험 메일의 실제 수신을 확인한 뒤에만 서비스의 root 전용 환경 파일을 설정하고 재시작하며, 건강 확인 실패 시 이전 설정으로 복원합니다. 자세한 순서는 [계정 관리 문서](account-management.md)를 참고하세요.
