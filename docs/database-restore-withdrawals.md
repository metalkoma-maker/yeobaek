# 탈퇴 계정이 포함된 DB 백업의 복원 준비

전체 DB 백업에는 백업 시점의 회원과 원고가 들어 있습니다. 그 뒤 탈퇴한 회원이 있다면 백업을 운영 DB에 그대로 덮어쓸 때 계정과 원고가 다시 나타날 수 있습니다. **운영 DB에 백업 파일을 바로 복사하지 마세요.** 배포 도구의 `rollback`은 코드만 되돌리며 DB를 자동으로 교체하지 않습니다.

`deploy/prepare_database_restore.py`는 복원 후보 파일을 **별도로** 만듭니다. 현재 운영 DB와 백업을 비교하거나, 활성화 후의 백업이라면 독립 탈퇴 기록을 확인해 탈퇴 회원과 연결된 원고·이력을 후보에서 삭제합니다. 이전 시점의 로그인 세션, 비밀번호 재설정 링크, 시도 제한 기록도 후보에서 제거합니다. 현재 DB와 원본 백업은 수정하지 않습니다. 출력에는 계정 수만 표시되며 ID·이메일·원고는 표시되지 않습니다.

## 독립 탈퇴 기록의 도입 순서

이 기능은 **아직 운영에 적용되지 않았습니다.** 운영 반영을 별도로 요청할 때 아래 두 단계를 같은 작업으로 검증합니다.

1. 운영 서버에서 `deploy/activate_withdrawal_ledger.py`를 관리자 권한으로 한 번 실행합니다. 이 도구는 기존 암호화 Google Drive 백업 공간에 새 기록의 시작 파일 두 개를 올려 다시 읽고, 운영 DB에 시작 표식과 삭제 보호 트리거를 추가합니다. 이 단계부터 새 앱 코드가 반영될 때까지 기존 탈퇴 요청은 차단될 수 있습니다. 원고·회원 행이나 기존 백업은 삭제하지 않습니다.
2. 새 앱 코드를 배포하고 시작·접속·가짜 계정의 탈퇴와 재시도를 확인합니다. 앱은 시작할 때 독립 기록의 시작 표식을 요구하고 Drive 기록을 읽어, 옛 DB에 다시 나타난 탈퇴 계정이 있으면 사용자 요청을 받기 전에 삭제합니다. 표식이나 Drive 기록을 확인하지 못하면 앱 시작을 중단합니다. 코드만 이전 버전으로 되돌려도 DB의 보호 트리거는 남아, 기록 없는 탈퇴를 막습니다.

탈퇴할 때에는 이메일이나 원고를 보내지 않고 내부 임의 회원 ID와 요청 시각만 기존 `rclone crypt` 원격지에 기록합니다. 기록을 다시 읽어 확인한 뒤 운영 DB에서 탈퇴를 완료합니다. Drive가 닿지 않거나 기록 검증이 실패하면 탈퇴는 완료되지 않고 계정의 추가 수정이 차단되며, 이용자는 탈퇴를 다시 시도해야 합니다. 이 시나리오는 운영 배포 전에 실제 가짜 계정으로 검증해야 합니다.

탈퇴가 완료되면 운영 DB의 임시 처리 행도 같은 트랜잭션에서 지웁니다. 독립 기록은 아래의 백업 점검을 통과할 때까지 남습니다.

## 탈퇴 기록의 보관 종료

사용자가 선택한 기준은 **탈퇴 요청 후 최소 30일이 지나고, 오래된 백업에서 해당 계정과 처리 중 기록이 모두 사라진 것을 확인한 뒤** 독립 기록을 삭제하는 것입니다. 30일이 지났다는 이유만으로 삭제하지 않습니다.

`deploy/prune_withdrawal_receipts.py`는 기본 실행에서 삭제 대상의 **개수만** 조사합니다. 현재 운영 DB, 7일 정기 로컬 백업, 30일 Drive 백업, 배포 직전 DB 사본을 모두 열어 `users`와 `withdrawal_requests`에 해당 ID가 남았는지 확인합니다. Drive의 기록과 백업을 읽을 수 없거나 DB 하나라도 손상되어 있으면 정리를 중단합니다. 기록 ID·이메일·원고는 출력하지 않습니다.

실제 삭제는 웹·백업 서비스를 중지하고 관리자가 위 위치 **밖의 수동 DB 사본까지 확인한 뒤** `--apply --other-copies-reviewed`를 지정해야 합니다. 실행 직전 목록을 다시 확인하고 Drive에서 삭제한 후 목록에서도 빠졌는지 확인합니다. 수동 사본이나 외부 저장소를 이 도구가 자동으로 찾을 수는 없습니다. 이 검토가 끝나지 않으면 기록을 계속 보관합니다. 아직 정기 자동 실행을 연결하지 않았으며 운영에도 적용되지 않았습니다.

## 사용할 수 있는 조건

1. 현재 운영 DB가 **탈퇴 후 상태를 보존하고 있고 읽을 수 있어야** 하거나, 백업이 독립 기록 활성화 **이후**에 만들어져 기록의 시작 표식과 Drive 기록을 검증할 수 있어야 합니다. 이미 오래된 백업으로 교체된 DB는 비교 기준으로 사용할 수 없습니다.
2. 서비스 쓰기를 중지한 뒤 현재 DB·WAL·SHM과 복원 대상 백업을 먼저 별도로 보존합니다. 후보를 만든 뒤에도 서비스를 중지한 상태에서 현재 DB와 후보를 비교합니다. 작업 중 새로운 탈퇴가 일어나면 후보를 폐기하고 다시 만듭니다.
3. 회원 ID가 유지되는 동일 서비스의 전체 SQLite 백업이어야 합니다. `users`, `manuscripts`, `sessions`, `password_resets`, `attempts` 표가 없거나 DB 무결성 검사에 실패하면 도구가 거절합니다.
4. 현재 DB가 유실되거나 신뢰할 수 없다면, 활성화 이후 백업과 검증된 Drive 기록이 둘 다 있을 때만 후보를 만들 수 있습니다. 활성화 이전 백업만 있거나 Drive 기록이 없으면 복원을 중단합니다.

## 격리된 사본으로 점검

경로는 실제 사고 상황에서 관리자가 확인한 것을 사용합니다. 다음 명령은 운영 DB를 교체하거나 서비스를 시작하지 않습니다.

```sh
python3 deploy/prepare_database_restore.py \
  --current /확인된/현재.sqlite3 \
  --backup /확인된/과거백업.sqlite3 \
  --output /보호된/작업폴더/복원후보.sqlite3
```

출력의 `removed_accounts`는 **백업에는 있으나 현재 DB에는 없는 회원의 수**입니다. 계정이 왜 사라졌는지까지 판별한 수치는 아닙니다. 후보를 운영에 적용할지는 별도의 복구 계획과 관리자 검토가 필요합니다. 백업 이후 회원이 쓴 글과 새로 가입한 계정은 과거 백업에 없으므로 이 도구가 복구하지 못합니다.

독립 기록 활성화 이후의 백업이라면 `--use-withdrawal-ledger`를 추가합니다. 현재 DB가 유실된 경우 `--current`를 생략하고 검증된 Drive 기록을 기준으로 후보를 만듭니다. 이 명령도 후보 파일만 만들며 운영 DB를 교체하지 않습니다.

```sh
python3 deploy/prepare_database_restore.py \
  --backup /확인된/활성화이후백업.sqlite3 \
  --output /보호된/작업폴더/복원후보.sqlite3 \
  --use-withdrawal-ledger
```

## 아직 남은 장애 상황

독립 기록을 활성화하기 **전**에 탈퇴한 회원은 별도 기록에 소급해 넣을 수 없습니다. 따라서 활성화 이전에 만든 백업을 현재 DB 없이 복원하지 않습니다. 활성화 이후에도 Google Drive 기록이 삭제·변조되거나 닿지 않으면 복원을 멈춥니다. 서버와 함께 `rclone` 암호화 설정까지 유실되면 Drive 백업과 탈퇴 기록을 읽기 위한 접근 복구가 먼저 필요합니다. 기록 파일 하나가 사라졌는데 그보다 오래된 DB만 남은 상황은 자동으로 완벽히 탐지할 수 없으므로, 저장소 접근 제한과 별도 점검이 필요합니다. 백업에 아직 필요한 계정이 없다는 검사는 관리 대상 위치에 한정됩니다. 수동 사본이 남아 있다면 기록 정리를 실행하지 않습니다.
