# 배포 전 DB 사본: 30일 보관

운영 배포 도구는 코드 교체 직전에 운영 DB 전체를 `state/backups/<UTC 시각>-<ID>/database.sqlite3`에 복사합니다. 이 사본은 장애 때 관리자가 수동으로 데이터를 확인·복구하기 위한 것입니다. 배포 도구의 자동 코드 되돌리기는 이 DB 파일을 사용하지 않습니다.

운영 정책은 **생성 시각부터 30일 보관**입니다. 한 시간마다 실행하는 정리 작업은 30일이 지난 배포 전 DB 사본 파일만 삭제합니다. 폴더의 `record.json`과 코드 복구 파일, 현재 운영 DB, 매시간 로컬 백업, 매일 Drive 백업은 대상이 아닙니다. 다음 시간 정리 때 삭제되므로 실제 보관은 대체로 30일에서 30일 1시간 사이입니다. 서버 작업이 멈추면 더 오래 남을 수 있습니다.

정리 작업은 `yeobaek-deploy` 계정으로 실행하며 배포 도구와 같은 잠금을 사용합니다. 배포 중이거나 복구 대기 상태이면 삭제하지 않습니다. 삭제 전에 대상 사본의 파일 유형·소유자·메타데이터를 확인하고, 하나라도 예상과 다르면 해당 실행에서는 아무 파일도 삭제하지 않습니다. `--inspect`로 삭제 예정 개수만 확인할 수 있습니다. 파일명과 DB 내용은 출력하지 않습니다.

`deploy/install_snapshot_retention.py`는 최초 한 번 root가 설치해야 합니다. 설치는 기존 웹 서비스와 운영 DB를 변경하지 않고 systemd 타이머를 등록합니다. 타이머를 켜면 첫 정리 작업이 바로 실행될 수 있으므로 설치 직전 `--inspect`에서 삭제 예정 개수를 먼저 확인합니다. 기존 GitHub Actions 배포 키에는 설치 권한이 없습니다. 배포 요청을 받은 뒤 검증된 고정 커밋과 체크섬을 사용해 설치 명령을 제공하고, 예약 상태와 첫 정리 결과를 확인해야 합니다. 설치 전에는 30일 자동 삭제가 **아직 적용되지 않은 상태**입니다.

회원 탈퇴는 활성 DB의 계정 데이터를 삭제하지만, 이미 만들어진 전체 DB 사본은 개별 계정을 즉시 지우지 못합니다. 복구 때 탈퇴한 계정 데이터가 되살아나지 않도록 하는 별도 복구 절차가 필요합니다. 이 30일 정책만으로 개인정보 처리방침의 백업 관련 확인 사항이 모두 해결되는 것은 아닙니다.
